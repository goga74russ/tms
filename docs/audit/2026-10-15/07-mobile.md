# Mobile Engineer — аудит TMS 2026-10-15

**Персона/взгляд:** мобильный инженер (Expo/React Native, offline-first). Смотрю глазами водителя на трассе без связи, в перчатках, на солнце, с телефоном, на котором токен истёк вчера. Главный вопрос: дойдёт ли до сервера то, что водитель сделал, ровно один раз и в нужном порядке.

**Охват:** `apps/mobile` целиком (App/index, navigation, context/AuthContext, api/* — sync, offlineQueue, upload, auth, client, trips, inspections, temperature, waybills, rto, wialonMock; database/* — schema, migrations, models; все 10 экранов; app.json, eas.json, package.json, plugins); серверная часть: `apps/api/src/modules/sync/{routes,service}.ts`, `trips/routes.ts` (start/complete/delivery-confirmation v2), `trips/service.ts` (changeTripStatus, createDeliveryConfirmation), `auth/rbac.ts`, `auth/auth.ts` (mobile login, TTL), `uploads/routes.ts`, `cold-chain/routes.ts`, `events/journal.ts`, `db/schema.ts` (events, delivery_confirmations), `packages/shared/src/enums.ts` (TRIP_STATE_TRANSITIONS); документы `docs/mobile/*`, `docs/operations/rustore-publish.md`, `apps/mobile/README.md`; прошлые отчёты `docs/qa/code-audit-2026-06-14.md`, `docs/qa/remediation-tracker.md`.

**Метод:** статическое чтение кода по сквозным сценариям (вход → список рейсов → старт → точка → доставка → завершение; офлайн → восстановление сети; истечение токена), сверка контракта клиент↔сервер (zod-схемы, RBAC, коды ответов). По каждой находке перечитал код второй раз и попытался её опровергнуть: искал альтернативные обработчики, другие права роли, нормализацию на сервере. Приложение на устройстве не запускал, это только чтение.

## Вердикт

Код мобильного приложения аккуратный: есть токены темы, SecureStore, dead-letter очередь, тесты экранов. Но **основной сценарий водителя end-to-end сейчас не работает**:
- подтверждение точки и завершение рейса отправляются с `id`, который не является UUID, сервер всегда отвечает 400, а водитель видит «Точка подтверждена» / «Рейс завершён»;
- кнопка «Начать рейс» для роли `driver` получает 403;
- экран подтверждения доставки недостижим из навигации.

API-смоук (`scripts/mobile-smoke.ps1`) генерирует корректные GUID, поэтому эти дефекты он не ловит. Offline-first заявлен, но устроен хрупко:
- `/sync/events` отвечает 200 даже на отклонённые события;
- нет идемпотентности для доставки и температуры;
- replay очереди идёт без блокировки;
- токен живёт 24 ч без refresh, а повторный запуск с истёкшим токеном **стирает всю офлайн-очередь**.

Локальная WatermelonDB синхронизируется только при старте приложения. После любого действия UI устаревает, новые рейсы появляются только после перезапуска. **Зрелость области: 3/10.** До пилота нужны исправления P0/P1 и обязательный прогон на устройстве (device gate из `docs/mobile/migration.md` до сих пор не закрыт).

## Сильные стороны

- JWT хранится в `expo-secure-store`, а не в AsyncStorage. PDF путевого листа открывается без токена в URL (B6.1).
- Офлайн-очередь: сериализованный `enqueueAction`, dead-letter вместо молчаливого удаления, сохранение повреждённых payload'ов, порядок «сначала dead-letter, потом усечение» (закрыто после аудита 2026-06-14).
- `uploadPhoto` с таймаутом 30 с, ретраями только на 5xx/сеть, фото с quality 0.6 для EDGE/3G.
- Серверный sync: проверка владельца рейса (C-7/C-8), обработка `cancelled` как конфликта с записью в журнал, `externalId` в `events` с уникальным индексом per-org, дельта точек по `updatedAt` (#569).
- UI: кнопки `lg` = 56 dp, основные действия в нижней sticky-панели, ETA-поллинг ставится на паузу в фоне, отдельный шаг проверки фото перед подписью.
- Пустая подпись получателя блокируется на клиенте, сервер дополнительно проверяет `data:image` regex.

## Находки

### [P0] MOB-01 — Подтверждение точки и завершение рейса никогда не доходят до сервера: id события не UUID
- **Где:** `apps/mobile/src/screens/CheckpointScreen.tsx:103`, `apps/mobile/src/screens/TripCompletionScreen.tsx:44`; сервер: `apps/api/src/modules/sync/routes.ts:22-45` (`id: z.string().uuid()`).
- **Что:** оба экрана генерируют `id: \`${Date.now()}_${random}\``. Сервер валидирует `z.string().uuid()` и отвечает **400** на весь пакет. Других обработчиков `/sync/events` нет. Корректный `uuidv4` есть только в неиспользуемом хелпере `confirmRoutePoint` (`api/trips.ts:179`).
- **Сценарий:** водитель онлайн подтверждает точку → 400 → `enqueueCheckpoint` → алерт «Точка сохранена… повторим». Replay снова получает 400 → 5 попыток → dead-letter, который UI не показывает (MOB-11). Точка на сервере остаётся `pending`, поэтому `changeTripStatus('completed')` падает с «Не все точки маршрута пройдены», а уведомление о подписи Т2 ЭТрН не создаётся. TripCompletion показывает экран «Рейс завершён», хотя рейс остаётся `in_transit`. Смоук-скрипт использует `[guid]::NewGuid()` и проходит, поэтому регрессия не видна.
- **Исправление:** `uuidv4()` в обоих экранах. Вынести построение событий в один модуль (`api/events.ts`) и покрыть контрактным тестом против zod-схемы сервера (общая схема в `packages/shared`).
- **Статус:** CONFIRMED

### [P0] MOB-02 — Водитель не может начать или завершить рейс из приложения: 403 на `/trips/:id/start` и `/complete`
- **Где:** `apps/api/src/modules/trips/routes.ts:524`, `:591` (`requireAbility('manage', 'Trip')`); `apps/api/src/auth/rbac.ts:150-163` (у `driver` только `read Trip`); клиент: `apps/mobile/src/screens/TripDetailsScreen.tsx:270-283`, `api/trips.ts` `startTrip`/`completeTrip`.
- **Что:** кнопки «Начать рейс» и «Завершить рейс» в sticky-панели вызывают эндпоинты, которые требуют `manage Trip`. У роли `driver` такого права нет (CASL: `read` не покрывает `manage`), и ни один общий блок его не выдаёт.
- **Сценарий:** у рейса `waybill_issued`, водитель жмёт «Начать рейс» и вводит одометр → 403 «Недостаточно прав». Рейс не переходит в `in_transit`, стартовый одометр и `odometerReadings` не пишутся. Единственный обходной путь — sync-событие (MOB-09), но там ломается MOB-01.
- **Исправление:** на этих двух роутах заменить проверку на «назначенный водитель рейса» (как `verifyTripOwnership` в sync) или выдать `driver` узкое право (например `can('execute','Trip')`) с проверкой владения. Добавить интеграционный тест с JWT роли `driver`.
- **Статус:** CONFIRMED

### [P0] MOB-03 — Истёкший токен (24 ч, без refresh) при следующем запуске стирает всю офлайн-очередь
- **Где:** `apps/mobile/src/context/AuthContext.tsx:52-60` → `apps/mobile/src/api/auth.ts:30-35` (`logout()` → `clearQueue()` удаляет основную очередь **и dead-letter**); TTL: `apps/api/src/auth/auth.ts:59` (`JWT_EXPIRES_IN = '24h'`), refresh-токена для mobile нет.
- **Что:** в `initAuth` любой 401/403 от `/auth/me` вызывает `apiLogout()`, а тот безусловно очищает очередь неотправленных действий.
- **Сценарий:** двухдневный рейс по трассе без связи. Водитель офлайн подтверждает доставку (подпись получателя, фото, данные паспорта) и пишет замеры температуры. Через 24+ ч появляется сеть, приложение перезапускается → `/auth/me` = 401 → очередь и dead-letter удалены без предупреждения. Юридически значимые подтверждения доставки и данные холодовой цепи потеряны. Если токен истекает при открытом приложении, replay получает 401 → 5 ретраев → dead-letter, а при следующем запуске то же самое удаление.
- **Исправление:** (1) при logout по истечению сессии **не** чистить очередь: привязать её к `userId` и очищать только при явном выходе другого пользователя, после подтверждения. (2) Добавить refresh-токен или скользящий mobile-TTL (7–30 дней) с отзывом по `tokenVersion`. (3) На 401 во время replay оставлять действия в очереди без инкремента `retries` и просить перелогиниться.
- **Статус:** CONFIRMED

### [P1] MOB-04 — `/sync/events` отвечает 200 на отклонённые события, клиент удаляет их из очереди
- **Где:** `apps/api/src/modules/sync/service.ts:34-57` (try/catch на каждое событие → `results.failed++`), `apps/api/src/modules/sync/routes.ts:212-213` (всегда `200 {success:true}`); клиент: `apps/mobile/src/api/offlineQueue.ts:232` (`res.ok` = успех), `CheckpointScreen.tsx:130`, `TripCompletionScreen.tsx:69`.
- **Что:** ошибка обработки события (точка не найдена, «не ваш рейс», «Не все точки маршрута пройдены», транзиентный сбой БД или deadlock) возвращается в теле как `data.failed/errors`, но HTTP-статус 200. Клиент тело не разбирает.
- **Сценарий:** после исправления MOB-01 водитель офлайн завершает рейс, а на сервере осталась незакрытая точка → `changeTripStatus` бросает исключение → 200 `{failed:1}` → действие удалено из очереди, водитель видит «Рейс завершён», рейс висит в `in_transit`. То же при временной ошибке Postgres: данные теряются без следа.
- **Исправление:** различать в ответе постоянные и временные ошибки (например `results.errors[].retryable`). Отдавать 207/422 при `failed>0` или разбирать тело на клиенте и оставлять в очереди retryable-события. Постоянные ошибки показывать водителю и диспетчеру.
- **Статус:** CONFIRMED

### [P1] MOB-05 — Сервер молча отбрасывает заметки о расхождениях, GPS и причину корректировки
- **Где:** `apps/api/src/modules/sync/routes.ts:9-20` (zod `object` без `notes/lat/lon/tripId/correctionReason` → поля удаляются при разборе); клиент: `CheckpointScreen.tsx:106-112` (`notes`), `TripCompletionScreen.tsx:47` (`correctionReason`), `api/trips.ts:179-205` (`lat/lon`).
- **Что:** поле «Заметки / расхождения» на экране точки и причина завершения рейса при блокерах (обязательная, не менее 6 символов) до БД не доходят. `updateRoutePoint` вызывается без них.
- **Сценарий:** при выгрузке водитель пишет «недостача 2 паллеты, пломба сорвана» → на сервере остаются только `status/photoUrls/signatureUrl`. Претензионный процесс и ЭТрН Т2 остаются без фиксации расхождения. Аудит корректировки при блокерах теряет обоснование.
- **Исправление:** добавить `notes`, `lat`, `lon`, `accuracy`, `correctionReason` в схемы и сохранять их (`route_points.notes`, событие в журнале). Схему вынести в `packages/shared` для клиента и сервера.
- **Статус:** CONFIRMED

### [P1] MOB-06 — `replayQueue` без блокировки: потеря действий, добавленных во время replay, и двойная отправка
- **Где:** `apps/mobile/src/api/offlineQueue.ts:203-263` (чтение очереди → долгий цикл с загрузкой фото → `setItem(QUEUE_KEY, remaining)` вне `withQueueWriteLock`), `:266-279` (`NetInfo` listener без in-flight флага).
- **Что:** (а) `enqueueAction`, выполненный во время replay, затирается финальным `setItem(remaining)`. (б) NetInfo шлёт несколько событий подряд (Wi-Fi→LTE, мигание `isInternetReachable`), и каждое запускает отдельный `replayQueue` по той же очереди.
- **Сценарий:** при въезде в зону покрытия очередь из 3 действий (каждое с фото) отправляется ~30 с. В это время водитель записывает температуру офлайн-путём (сеть «прыгает») → запись пропадает. Параллельно второй replay отправляет те же подтверждение доставки и замер ещё раз, а идемпотентности нет (MOB-07).
- **Исправление:** единый мьютекс на replay и запись очереди, флаг `isReplaying`. Удалять из очереди по `id` только успешно отправленные действия (merge с текущей очередью), а не перезаписывать её целиком.
- **Статус:** CONFIRMED — повтор: remediation-tracker «P1 `offlineQueue.ts:149-206` — replayQueue без блокировки (DEFER → mobile-проход)», не закрыто

### [P1] MOB-07 — Нет идемпотентности для доставки и температуры; `createDeliveryConfirmation` не транзакционна и множит записи
- **Где:** `apps/api/src/modules/trips/service.ts:1547-1597` (insert `delivery_confirmations` → `recordEvent` → `changeTripStatus('completed')` без транзакции); `db/schema.ts` (`delivery_confirmations`: нет unique по `trip_id` / idempotency-key); `cold-chain/routes.ts:45`; клиент `offlineQueue.ts:224-231`, `api/temperature.ts:96-142` (нет `Idempotency-Key`). Поддержка `Idempotency-Key` в API есть только у ЮKassa.

Если `changeTripStatus` бросает исключение (точки не закрыты, что сейчас всегда так из-за MOB-01), подтверждение уже вставлено, ответ 400, клиент ретраит до 5 раз → до 6 одинаковых подтверждений доставки.

Дубли попадают в пакет транспортных документов (`refreshTransportDocumentsForTrip`) и в отчётность. Замеры температуры дублируются при каждом повторе и искажают SLA и инциденты.

Обернуть insert и смену статуса в одну транзакцию. На клиенте считать 409 «уже принято» только при совпадении ключа.
- **Статус:** CONFIRMED — повтор (часть про температуру): remediation-tracker «P1 `temperature.ts:86` + `cold-chain/service.ts:122` — idempotency-ключ (DEFER → mobile-проход)», не закрыто

### [P1] MOB-09 — Через sync-события водитель может отменить свой рейс или перевести его в `billed` (обход RBAC)
- **Где:** `apps/api/src/modules/sync/service.ts:72-100` (`trip_status_changed` → `changeTripStatus(tripId, status)` с любой строкой, проверяется только владение); `apps/api/src/modules/sync/routes.ts:9-14` (`status: z.string().min(1)`); `packages/shared/src/enums.ts:389-400` (`ASSIGNED/WAYBILL_*/LOADING → CANCELLED`, `COMPLETED → BILLED`).
- **Что:** sync-путь обходит ограничение `manage Trip`, которое действует на REST (MOB-02). Разрешён любой переход по машине состояний.
- **Сценарий:** водитель (или скрипт с его JWT) отправляет `{type:'trip_status_changed', payload:{tripId, status:'cancelled'}}` для назначенного рейса → рейс отменён без диспетчера. Или `completed → billed`: рейс помечен выставленным без счёта, что ломает биллинг и сверку.
- **Исправление:** для sync разрешать только whitelist статусов водителя (`completed`, при необходимости `loading/in_transit` с теми же гейтами, что `/start`). Всё остальное отклонять как `forbidden_transition`.
- **Статус:** CONFIRMED

### [P1] MOB-10 — Локальная БД синхронизируется только при запуске: UI устаревает, новые рейсы не видны, действия повторяются
- **Где:** `apps/mobile/src/context/AuthContext.tsx:49`, `:77` — единственные вызовы `syncDatabase`. `TripDetailsScreen.tsx:133-146` и `:245-247` берут статус рейса и точек из WatermelonDB. Pull-to-refresh, периодического sync и sync по `AppState` нет. После действий локальные записи не обновляются.
- **Что:** после «Начать рейс» или подтверждения точки `fetchData()` читает старые локальные данные. Кнопки `canStart` и «Подтвердить» остаются активными, `canComplete` не включается.
- **Сценарий:** диспетчер днём назначает водителю новый рейс → в «Мои рейсы» его нет, пока приложение не убито и не запущено заново. После подтверждения точки она по-прежнему показана как «Ожидает» → водитель подтверждает ещё раз (повторная загрузка фото, дубли событий).
- **Исправление:** вызывать `syncDatabase` после каждой успешной мутации, при `AppState → active`, по pull-to-refresh и при восстановлении сети. Делать оптимистичное локальное обновление статуса точки или рейса с пометкой «ожидает синхронизации».
- **Статус:** CONFIRMED

### [P1] MOB-11 — Dead-letter очередь невидима, постоянные 4xx ретраятся вслепую, replay только при смене сети
- **Где:** `apps/mobile/src/api/offlineQueue.ts:232-256` (любой не-2xx, кроме 409, → `retries++`, после 5 попыток → dead-letter); `getFailedCount/getFailedQueue` нигде в UI не используются (используется только `getQueueSummary` в `TripDetailsScreen.tsx:149`); `:266-279` replay только по событию NetInfo.
- **Что:** валидационные и бизнес-ошибки (400/403/404/422) неотличимы от сетевых. После 5 попыток действие тихо уходит в dead-letter, водитель и диспетчер об этом не узнают. Если сеть есть, а сервер отвечал 5xx, следующей попытки не будет до смены состояния сети.
- **Сценарий:** все 100% подтверждений точек из-за MOB-01 оказываются в dead-letter, UI показывает «Все данные синхронизируются». Диспетчер видит невыполненные точки, водитель уверен, что всё отправлено.
- **Исправление:** классифицировать ответы (4xx, кроме 401/408/429, — постоянная ошибка: сразу в dead-letter с причиной). Экран или баннер «Не отправлено: N» с повтором, просмотром и экспортом. Экспоненциальный backoff по таймеру и по `AppState → active`. Отправлять телеметрию dead-letter на сервер.

### [P2] MOB-16 — Персональные данные офлайн-очереди лежат на устройстве открыто, резервное копирование Android не отключено
