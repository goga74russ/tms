### [P1] QA-01 — CI-гейт красный 4 месяца, downstream-гейты не запускались с 14.06.2026
- **Где:** `.github/workflows/p0-gate.yml:62-90` (шаг «OpenAPI spec sync check»), `docs/api/openapi.json`, `docs/api/openapi.md`
- **Что:** `gh run list`: из последних 100 прогонов P0 Gate 55 красные, **последние 50 подряд**, с 2026-06-14T07:58Z до последнего коммита 2026-07-03. Каждый раз падает `build-and-static-gates` на OpenAPI drift. Jobs `smoke-chain`, `playwright`, `api-integration` объявлены с `needs: build-and-static-gates` и поэтому **ни разу не стартовали** (`- smoke-chain in 0s`). Шаги «Web component tests» и «Mobile unit tests» тоже пропускаются, потому что идут после упавшего шага. Коммиты продолжали вливаться в `main` на красном гейте. Branch protection проверить не смог: API отвечает 403.
- **Сценарий:** локально воспроизведено: `openapi:export` даёт +3 маршрута и новое summary webhook. Пока гейт был красным, накопились QA-02, QA-03 и QA-09, а команда этого не видела.
- **Исправление:** закоммитить актуальный `openapi:export`. Включить branch protection с required checks на все 4 job. Вынести drift-check в отдельный job, чтобы он не блокировал тестовые jobs и не прятал их результат. Добавить в Definition of Done правило: «main красный — это стоп-линия».
- **Статус:** CONFIRMED.

### [P1] QA-04 — Telegram deep-link привязывает чат к организации по непроверяемому userId (P1 аудита 06-14 не закрыт)
- **Где:** `apps/api/src/modules/notifications/routes.ts:43-71`
- **Что:** userId из `/start <userId>` проверяется только на формат UUID. Из него берётся `organizationId`, и подписка создаётся с `eventTypes: ['*']`. Владение userId ничем не подтверждается: нет одноразового nonce и нет подтверждения в приложении.
- **Сценарий:** злоумышленник, знающий UUID пользователя чужой организации (UUID встречаются в ссылках, экспортах, логах, у бывших сотрудников), отправляет боту `/start <uuid>` и начинает получать все события этой организации: рейсы, счета, путевые листы.
- **Исправление:** одноразовый короткоживущий токен, который выдаётся в ЛК (`POST /notifications/telegram/link-token`), в deep-link передаётся токен, а не userId. Плюс интеграционный тест на подделанный payload.
- **Статус:** CONFIRMED; повтор: code-audit-2026-06-14 P1 «Telegram /start deep-link», не закрыто (в аудите помечено «требует продуктового решения»).

### [P1] QA-05 — Rate-limit логина обходится ротацией X-Forwarded-For (P1 #1 аудита закрыт наполовину)
- **Где:** `apps/api/src/server.ts:116` (`trustProxy: true`), `apps/api/src/server.ts:217-220` (`keyGenerator → ip:${request.ip}`), `nginx/default.conf:33` (`$proxy_add_x_forwarded_for`)
- **Что:** фикс `28207d2` закрыл только loopback-обход через allowList (`server.ts:227`, теперь по `socket.remoteAddress`). Вторую половину той же находки («keyGenerator становится управляемым») не исправили. При `trustProxy: true` Fastify берёт **крайний левый** адрес из XFF, а nginx дописывает реальный IP справа, поэтому клиентский XFF сохраняется. Блокировки учётной записи по числу неудачных попыток нет (grep `lockout|failedLogin|lockedUntil` ничего не находит).
- **Сценарий:** `for i in …; curl -H "X-Forwarded-For: 10.0.$i.1" -d '{"email":"victim",…}' /api/auth/login`: каждый запрос попадает в новый бакет, лимит 5/мин не срабатывает. Так же перебираются 6-значные коды verify-email и reset.
- **Исправление:** `trustProxy: '<IP nginx>'` или `trustProxy: 1`, либо в nginx `proxy_set_header X-Forwarded-For $remote_addr`. Дополнительно счётчик неудачных попыток по email. Нужен регресс-тест: два запроса с разным XFF должны попадать в один бакет.
- **Статус:** CONFIRMED (по коду и семантике proxy-addr; живой прогон через nginx не делал). Повтор: code-audit-2026-06-14 P1 #1, закрыт частично.

### [P1] QA-06 — Мобильная офлайн-очередь: replay без блокировки, действия, поставленные во время replay, теряются
- **Где:** `apps/mobile/src/api/offlineQueue.ts:203-262` (replayQueue), `:82-93` (enqueueAction), `:265-276` (setupAutoReplay)
- **Что:** `replayQueue` читает очередь, отправляет действия по сети, а в конце **перезаписывает** `QUEUE_KEY` массивом `remaining`, вычисленным из снимка на момент старта. Мьютекса нет. Повторные события NetInfo (сеть «моргает») запускают параллельные replay.
- **Сценарий:** (а) водитель офлайн подтверждает доставку, пока идёт replay: `enqueueAction` дописывает действие, затем replay записывает `remaining` и стирает его. Подтверждение доставки теряется молча. (б) Два replay одновременно отправляют одно действие дважды, а неидемпотентные POST создают дубли (замеры температуры, отметки точек).
- **Исправление:** in-memory lock (флаг или promise) вокруг replay. Удалять из очереди по id, а не перезаписывать её целиком. Idempotency-key в каждом действии, с проверкой на сервере. Нужен jest-тест: enqueue во время replay и двойной replay.
- **Статус:** CONFIRMED; повтор: remediation-tracker C5 «offlineQueue.ts:149-206 replayQueue без блокировки», DEFER, не закрыто.

### [P2] QA-14 — UI по умолчанию предлагает НДС 20% в 2026 году, сервер на каждом выпуске отвечает 422
