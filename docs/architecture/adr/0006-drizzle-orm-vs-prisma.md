# ADR-0006: Drizzle ORM over Prisma for the API data layer

- **Status:** Accepted
- **Date:** 2026-03-15 (date of first migration, `0000_full_schema`)
- **Deciders:** TMS core team

## Context

The API talks to a single Postgres 16 instance and needs:

1. Strong TypeScript types for every column, including `jsonb`, `uuid`, enums, generated columns, and our domain types.
2. Plain-SQL migrations we can review like any other code change (the schema carries trigger logic for the append-only `events` table — see ADR-0003 — and DB-level constraints we don't want hidden behind a code-gen layer).
3. Docker images small enough to ship — every megabyte in the runtime matters when we deploy to client VPS hosts.
4. Native Postgres types without translation gymnastics.

Alternatives considered:

- **Prisma** — Best-in-class DX, generated client, nice `include`/`select` ergonomics. Costs: a separate code-gen step in the build pipeline, ~50 MB of runtime artefacts (`@prisma/engines`, query engine binaries per platform), schema-DSL drift from real SQL, and trigger/RLS support that fights the generator.
- **Knex / Kysely** — Good query builders but no automatic types from schema; we'd hand-write type definitions next to the migrations.
- **Raw SQL + `postgres.js`** — Maximum control, zero type safety. Past pain.

## Decision

Use **Drizzle ORM**. Schema is declared in TypeScript at `apps/api/src/db/schema.ts`; migrations are plain `.sql` files in `apps/api/drizzle/` generated by `drizzle-kit generate` from schema diffs, then hand-tuned where needed.

Mechanism:

- `drizzle-kit generate` produces the SQL migration; the developer reviews and edits.
- `drizzle-kit migrate` applies migrations in CI and at deploy time.
- TypeScript types flow from the schema declaration — no code-gen step.

## Consequences

**Positive**
- Bundle stays tiny: no engine binaries, no generator output, no separate runtime package.
- Migrations are SQL files we can grep, diff, and review like any other change. Triggers and constraints live next to the column they protect.
- Native Postgres types (`jsonb`, `uuid`, enums, arrays) work without conversion shims.
- Row-level security and DB-level multi-tenancy (ADR-0001) integrate cleanly — Drizzle doesn't fight `SET app.organization_id`.

**Negative**
- No Prisma-style `include` graph queries — every join is written explicitly. More code in modules with deep relations (e.g. trip → driver → vehicle).
- Smaller ecosystem; fewer third-party plugins, no Prisma Studio equivalent for ad-hoc inspection (we use `psql` or a desktop client).

**Neutral**
- `schema.ts` is the source of truth. Diffing schema vs database is `drizzle-kit check` (run as an advisory gate in CI).
- Migration tags use timestamps from `_journal.json`, not semver — easier to chronologically order across branches.
