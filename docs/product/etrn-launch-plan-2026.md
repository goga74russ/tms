## 0. TL;DR

С 01.09.2026 все коммерческие грузоперевозки в РФ обязаны вестись через ЭПД в ГИС ЭПД (ФЗ-140, поправки в УАТ 259-ФЗ, 87-ФЗ, ВК, УЖТ). Бумага — только по исключительному перечню Минтранса.

Готовность TMS-prod на 2026-05-15: **~35%** — модель данных и архитектура есть, боевой обмен не подключён.

До дедлайна **108 календарных / ~75 рабочих дней**. Критический путь — договор и sandbox оператора ЭДО (5–10 рабочих дней). Без него никакая разработка не валидируется.

Цель этого документа:
1. Зафиксировать минимально-жизнеспособный (MVP) и полный сценарий с датами.
2. Дать операционному владельцу чек-листы и шаблоны для коммерческой работы.
3. Превратить compliance-проект в продаваемый пакет «TMS + ЭТрН под ключ».

## 2. Два сценария запуска

### 2.1. MVP — минимум для легитимного 01.09.2026

Цель: можно легально работать через одного оператора с базовым набором титулов.

| Что | Срок |
|---|---|
| Один оператор (рекомендация — Контур.Диадок) | договор + sandbox |
| Title 01, 02, 04, 05, 06 — XML генераторы | все 5 |
| XSD-валидация перед send (libxmljs2) | да |
| КЭП юрлица через Контур.Подпись + Госключ для водителей | да |
| МЧД-модель (минимальная: ФИО, СНИЛС, полномочия, срок) | да |
| Per-title callback-handler с идемпотентностью | да |
| UAT-цикл в sandbox оператора | да |
| Бумажное исключение с reason-code Минтранса | да |
| Архив XML + подписей ≥5 лет | да |

**Объём:** 4–5 недель работы одного-двух разработчиков.
**Релиз-дата:** **20.08.2026** (10-дневный буфер до закона).

### 2.2. Полный сценарий — пакет «коробка под 01.09»

Всё из MVP +

- Title 03 (переадресация), Title 07/08 (ПУД-обмен у грузоотправителя).
- Сопроводительные ведомости (ОН_SOPVEDPER/GO/GP) — для ADR и опасных грузов.
- Заказ-заявка (ON_ZAKAZNAR_*) — 4 титула.
- Второй оператор (СБИС или Такском) — резервный, для клиентов с другим контуром.
- CADES Plugin для подписи в браузере (для клиентов без облачной КЭП).
- Мобильный офлайн-доступ к ЭТрН + QR.
- Делегирование «отправитель → экспедитор → перевозчик».
- Refusal/rejection workflow в веб-кабинете.

**Объём:** 8–10 недель.
**Релиз-дата:** **01.07.2026** — пилотные клиенты, **15.07.2026** — общий запуск.

## 4. Технические задачи (детально)

### 4.1. МЧД (машиночитаемая доверенность)

С 01.09.2024 МЧД обязательна для подписи документов от юрлица сотрудником. Без неё ЭТрН не принимается ГИС ЭПД.

Минимальная модель:

```ts
type Mchd = {
  id: string;
  organizationId: string;
  doverittel: { inn: string; ogrn: string; name: string }; // юрлицо
  doverenny: { fio: string; snils: string; inn?: string }; // сотрудник
  powers: MchdPower[]; // справочник полномочий
  signedAt: Date;
  validFrom: Date;
  validTo: Date;
  registryNumber: string; // номер в реестре ФНС/Минцифры
  status: 'active' | 'revoked' | 'expired';
  xmlPayload: string; // подписанный XML МЧД
};
```

Валидация подписи титула должна проверять: подписант = doverenny в активной МЧД с полномочием для этого титула.

### 4.2. Генераторы T02, T03, T05, T06, T07, T08

Подключить XSD ФНС (приказ ЕД-7-26/1065@) из `D:\Ai\TMS\docs\etrn\` (см. [architecture/etrn-source-map.md](../architecture/etrn-source-map.md)). Структура каждого титула:

- `Файл` → корневой
- `СвУчДО` → сведения об участниках документооборота
- `Документ` → версия формата, КНД, наименование
- `Сведения...` → специфичный блок титула

Использовать общий билдер для повторяющихся блоков (участники, перевозчик, ТС, водитель), специфика — только в Сведениях.

### 4.3. XSD-валидация

Текущий чекер в `apps/api/scripts/check-etrn-xsd-fixtures.ts` — фикстурный. Производственный гейт:

```ts
// apps/api/src/modules/etrn/xsd-validator.ts
import libxml from 'libxmljs2';
import { XSD_MANIFEST } from '../trips/etrn-xsd-manifest';

export function validateEtrnXml(titleType: EtrnTitleType, xml: string): ValidationResult {
  const xsdPath = XSD_MANIFEST[titleType];
  const xsdDoc = libxml.parseXml(fs.readFileSync(xsdPath));
  const doc = libxml.parseXml(xml);
  return { ok: doc.validate(xsdDoc), errors: doc.validationErrors };
}
```

Гейт ставится **перед** `EdiProvider.sendDocument()`. Если не прошло — fail fast, статус `BLOCKED`, событие в timeline.

### 4.4. Per-title идемпотентность

Сейчас `apps/api/src/modules/edi/service.ts` прогрессит на уровне рейса. Нужно:

- Уникальный ключ обмена = `(documentId, titleType, externalMessageId)`.
- Callback-обработчик матчит по этому ключу, не по trip.id.
- Дубликаты от оператора (re-delivery) идемпотентно игнорируются.

### 4.5. Архивная политика

Минимум 5 лет (НК РФ + правила ЭДО). Что хранить:

- Исходный XML каждого титула.
- Все подписи (КЭП + МЧД).
- Provider IDs (диадок-message-id, gisepd-document-id).
- Полная timeline истории статусов.
- Снимки сертификатов на момент подписи (subject, issuer, valid period).

S3-bucket с object-lock + cold-storage rotation после 1 года.

## 5. Сравнение операторов ЭДО — чек-лист вопросов

Отправлять одинаковый РКП в **Контур.Диадок**, **СБИС**, **Такском**, опционально **Калуга-Астрал** и **ЭДО.Поток**.

### 5.1. Технические

1. Версия API для ЭПД (REST/SOAP, ссылки на актуальную документацию).
2. Срок выдачи sandbox-кредов с момента подписания (целимся в ≤5 рабочих дней).
3. Поддерживаются ли все 8 титулов ЭТрН, заказ-заявка, сопроводительные ведомости?
4. Какой формат коллбеков (webhook / long-polling / push)? Есть ли SLA на доставку?
5. Идемпотентность повторных send — на стороне оператора или клиента?
6. Лимиты на размер XML, RPS на send, кол-во документов в сутки.
7. Тестовый контур ГИС ЭПД доступен через них или нужно отдельно подключаться к Минтрансу?
8. Поддержка МЧД: проверка валидности при отправке, источник реестра.

### 5.2. Подпись

9. Что предлагают для КЭП юрлица: облачная подпись, локальный криптопровайдер, CADES-плагин?
10. Поддержка Госключа для водителей (deeplink-сценарий)?
11. Цена выпуска КЭП юрлица и продления (для перепродажи клиентам).

### 5.3. Коммерческие

12. Тарифные планы: pay-per-document / абонемент / гибрид.
13. Цена за исходящий комплект ЭТрН (8 титулов).
14. Цена за входящий комплект.
15. Скидки за объём (1k / 10k / 100k документов в месяц).
16. White-label / API-only тариф (без их веб-кабинета — для нашего embedded use case).
17. Возможность реселлинга — наши клиенты идут через нас или прямые контракты?
18. SLA: uptime, время реакции на инциденты, штрафы.

### 5.4. Юридические

19. Подтверждение аккредитации Минтрансом (приказ, дата).
20. Готовая оферта или нужен индивидуальный договор?
21. Условия по обработке ПДн (мы как оператор ПДн → они как обработчик).
22. Гарантии хранения архива ≥5 лет.

### 5.5. Решение

Решение фиксируем в [docs/architecture/adr/](../architecture/adr/) как ADR-0010 «EDI Operator Selection».

Базовая рекомендация — **Контур.Диадок**:
- крупнейший игрок, стабильный API;
- сами выпускают КЭП → один контрагент на ЭДО + подпись;
- встроенная поддержка МЧД и Госключа;
- есть white-label;
- быстрый sandbox (по практике 3–5 дней).

Резерв — **СБИС** (для клиентов «на СБИСе», их много в логистике).

## 6. Юридический пакет (продаваемые шаблоны)

Это не наше внутреннее, это то, что мы кладём в коробку для клиента-перевозчика. На рынке этого катастрофически не хватает, можно монетизировать отдельно.

### 6.1. Внутренний приказ заказчика «О переходе на ЭПД»

Шаблон-болванка для клиента (его юрлицо):

- Назначить ответственного за ЭПД (обычно главный логист / IT-директор).
- Утвердить регламент работы с ЭПД (см. 6.2).
- Утвердить перечень сотрудников-подписантов и их полномочия для МЧД.
- Утвердить оператора ЭДО и порядок взаимодействия.
- Срок ввода в действие — не позднее 01.09.2026.

### 6.2. Регламент работы с ЭПД

Разделы:

1. Термины и определения (ЭПД, ЭТрН, ГИС ЭПД, оператор, КЭП, МЧД, титулы).
2. Состав электронных перевозочных документов.
3. Порядок формирования ЭТрН (роли, последовательность титулов).
4. Применение электронной подписи.
5. Действия при сбоях оператора и ГИС ЭПД.
6. Бумажное исключение (исключительный перечень Минтранса).
7. Хранение и архивация (≥5 лет, ответственный, место).
8. Действия при отказе/корректировке титула.
9. Взаимодействие с контрагентами (грузоотправитель / перевозчик / грузополучатель / экспедитор).

### 6.3. Допсоглашение к договору перевозки (универсальный шаблон)

Ключевые положения:

- «Стороны переходят на электронные перевозочные документы в соответствии с ФЗ-140, ФЗ-259, 87-ФЗ с момента подписания соглашения, но не позднее 01.09.2026».
- Указание оператора(-ов) ЭДО, их роуминга.
- Распределение титулов: какая Сторона формирует, кто подписывает, в какой срок.
- Сроки подписания каждого титула (например, T02 — в течение 24 часов с момента получения T01).
- Применяемые ЭЦП: вид (КЭП/УКЭП), удостоверяющий центр, МЧД.
- Признание электронных документов равнозначными бумажным.
- Действия при невозможности использования ЭПД (force majeure ГИС ЭПД, отзыв аккредитации оператора).
- Ответственность за непередачу/несвоевременную передачу титулов в ГИС ЭПД (штраф / неустойка).
- Порядок исправления и корректировки.
- Хранение и предоставление по запросу контрагента, ФНС, ФССП.

### 6.4. Допсоглашение к договору транспортной экспедиции

То же + специфика экспедитора:

- Поручение экспедитору в электронном виде.
- Экспедиторская расписка как ЭПД.
- Складская расписка.
- Делегирование подписи привлечённому перевозчику (через МЧД).

### 6.5. Согласие сотрудника на использование КЭП

Шаблон-болванка для каждого сотрудника-подписанта:

- Согласие на выпуск КЭП.
- Согласие на использование МЧД от имени работодателя.
- Согласие на обработку ПДн оператором ЭДО.
- Признание электронных документов, подписанных КЭП работника, равнозначными собственноручно подписанным.

### 6.6. Согласие водителя на ЭТрН через Госключ

Отдельно — потому что водители часто работают как самозанятые или по ГПХ:

- Согласие на использование Госключа для подписи Title 04/05/06.
- Установка приложения Госключа как обязательное требование.
- Альтернатива (если нет смартфона) — подпись грузополучателем в присутствии водителя.

### 6.7. Где это разместить в продукте

- `docs/legal/etrn/` — мастер-шаблоны (markdown + docx generation).
- В UI веб-кабинета: онбординг-визард «Подготовка к 01.09» с генерацией пакета документов клиента (подставляет реквизиты, выбор оператора, состав сотрудников).
- Тариф: либо включено в premium-план TMS, либо отдельная позиция «ЭТрН Compliance Pack» (3–5k ₽/месяц с клиента).

## 7. Риски и митигации

| Риск | Вероятность | Импакт | Митигация |
|---|---|---|---|
| Sandbox оператора получаем позже чем за 10 дней | Высокая | Критический | Параллельно подаваться к 2–3 операторам |
| ФНС меняет XSD за 2 месяца до дедлайна | Средняя | Высокий | Мониторить ФНС-приказы, XSD-манифест версионируем, CI на свежие схемы |
| Сертификаты КЭП клиентов протухают / не выпущены вовремя | Высокая | Высокий | В онбординге проверка валидности КЭП, алерты за 30/14/7 дней до истечения |
| МЧД-реестр Минцифры падает / не отвечает | Средняя | Высокий | Кэширование подтверждений МЧД на 24 часа, graceful degradation |
| Клиенты не успевают подписать допсоглашения | Высокая | Средний | Шаблоны готовы заранее, в UI — мастер с авто-генерацией |
| Водители без смартфонов / не ставят Госключ | Средняя | Средний | Fallback: подпись грузополучателем за водителя (с фиксацией) — пока разрешено в бумажном исключении |
| ГИС ЭПД даун в день закона | Низкая | Критический | Очередь отложенных send, ретраи с exponential backoff, бумажное исключение по reason-code «недоступность ГИС» |
| Конкуренты (1С, Деловые Линии) выходят первыми | Высокая | Стратегический | Сосредоточиться на нише middle-market (там 1С неудобен, Деловые Линии не продают TMS отдельно) |

## 8. Метрики готовности (дашборд)

Что мониторим в [operations/monitoring/](../operations/monitoring/) после релиза:

- `etrn_titles_generated_total{titleType, status}` — счётчик сгенерированных.
- `etrn_titles_sent_total{operator, titleType, result}` — отправки.
- `etrn_titles_signed_total{titleType, signerRole}` — подписи.
- `etrn_xsd_validation_failures_total` — провалы XSD-валидации (должно быть ~0).
- `etrn_callback_latency_seconds{operator, titleType}` — латентность коллбеков.
- `etrn_titles_stuck` — gauge титулов застрявших в SENT > 24h (алерт > 0).
- `etrn_paper_exceptions_total{reasonCode}` — бумажные исключения по причине.
- `etrn_mchd_validation_failures_total` — провалы проверки МЧД.

Алерт-правила в [operations/monitoring/alert-rules.md](../operations/monitoring/alert-rules.md) дополнить ЭТрН-секцией.

## 9. Коммерческая упаковка (отдельно от compliance)

Compliance-проект → продукт «TMS + ЭТрН под ключ»:

1. **Базовый TMS** (текущий продукт) — ничего не меняется.
2. **Модуль ЭТрН** — отдельный SKU, включает обмен через оператора, КЭП, МЧД, шаблоны юр-пакета. Премиум-фича.
3. **Compliance Pack** — pdf-генерация юр-пакета (приказ, регламент, допсоглашения). Опция при покупке Модуля ЭТрН либо отдельный SKU для тех, у кого свой ЭДО.
4. **White-label для бухгалтеров и юристов** — бухгалтерская / юридическая фирма продаёт нашу коробку своим клиентам-перевозчикам, с их брендом.

Маркетинг до 01.09:

- Лендинг «Готов ли ваш TMS к 01.09.2026» с чек-листом самооценки.
- Вебинар «Что такое ЭТрН и почему ваша бухгалтерия сядет в лужу 02.09» (с приглашением 1–2 экспертов отрасли).
- Кейсы пилотных клиентов после июля.
