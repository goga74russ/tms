## §1 Конкретный дефект пользователя — `print/act/[id]/page.tsx`

Скрин выгрузки: УПД-2026-00001 от 10.06.2026, ИП Бардин → ИП Никитин, 48 000 ₽ (40 000 + НДС 20% 8 000). **Таблица услуг пуста.**

### 1.1 🔴 Терминологическая каша «АКТ» vs «УПД»

**Код** (строка 71): `<div className="doc-title">АКТ ВЫПОЛНЕННЫХ РАБОТ</div>` — жёстко захардкожен.

**Реальный номер** документа: `inv.number = 'УПД-2026-00001'` — пришёл из БД (видимо, номер инвойса с типом `upd` сгенерирован с префиксом «УПД»).

В подвале (строка 162): «Акт № УПД-2026-00001».

**Юр-импликация:** УПД — это **отдельный документ** по приказу ФНС ЕД-7-26/901@, заменяющий связку СФ + Акт. Документ с заголовком «АКТ ВЫПОЛНЕННЫХ РАБОТ» и номером «УПД-...» не признаётся ни как акт, ни как УПД:
- Для УПД отсутствуют обязательные реквизиты: статус 1/2, дата фактической отгрузки/услуги, подписи передающей и принимающей сторон (в УПД они **обязательны и раздельны**), ссылка на нормативку.
- Для акта используется чужая нумерация (УПД-префикс), что вводит контрагентов и ФНС в заблуждение.

**Корневая причина:** этот шаблон вызывается через маршрут `/print/act/[id]`, но в БД хранится запись типа `upd` (по моей invoice-spec.md, после M-batch есть enum `invoice_type` с 7 значениями). Когда пользователь кликает «печать акта» для записи типа `upd`, открывается **не тот** шаблон.

**ТЗ для TransPult:**
- Перенаправить пользователя на корректный шаблон в зависимости от `invoice.type`:
  - `type='act'` → `/print/act/[id]`
  - `type='upd'` → `/print/upd/[id]`
  - `type='sf'` → `/print/sf/[id]`
  - `type='corrective_sf'`/`'corrective_upd'` → `/print/corrective-sf/[id]`
  - `type='payment'`/`'advance'` → `/print/invoice/[id]`
- Это auto-routing (§5.5 моего invoice-spec-acceptance-O.md), который я отметил как «не блокирующее» — но он **становится блокирующим**, когда пользователь нажимает «печать акта» на УПД-записи и получает мутацию.
- Альтернатива: добавить guard в шаблон `act/[id]` — если `inv.type !== 'act'` → редирект или сообщение «Этот документ имеет тип «{type}»; используйте соответствующий шаблон».

### 1.2 🔴 Пустая таблица услуг — фундаментальный дефект

**Код** (строка 60): `const tripRows: any[] = Array.isArray(inv.tripRows) ? inv.tripRows : [];`

**API**: `GET /api/finance/invoices/${id}` — возвращает `data` объект. Поле `tripRows` в этом объекте либо **не передаётся** бэкендом, либо передаётся пустым массивом для записей типа `upd` (потому что `tripRows` — legacy-поле, M-batch заменил его на `invoice_orders` junction).

В шаблоне строка 109-122 содержит fallback: `tripRows.length === 0` → «Данные о рейсах не указаны». **Но на скрине этой надписи нет** — значит fallback не сработал. Возможные причины:
- CSS-конфликт (надпись есть, но цвет белый/невидимый при печати).
- `tripRows` — не undefined и не [], а нечто, что прошло `Array.isArray` true, но при этом `.length === 0` false (маловероятно).
- PDF-генератор обрезает фолбэк-строку.

**Юр-импликация:** документ без перечня оказанных услуг **не соответствует** ст. 9 ФЗ-402 «О бухучёте» — отсутствует обязательный реквизит «содержание факта хозяйственной жизни». Заказчик не сможет принять расход к учёту (ст. 252 НК), ФНС при проверке аннулирует документ.

**ТЗ для TransPult:**
1. Бэкенд: при возврате `GET /finance/invoices/:id` для документов типа `act`/`upd` обязательно агрегировать рейсы из `invoice_orders` junction → возвращать в поле `orders[]` (как в SF-шаблоне) с реквизитами:
   ```
   orderNumber, tripNumber, date, route (loadingAddress → unloadingAddress), distanceKm, allocatedAmount, cargoDescription
   ```
2. Шаблон: использовать `inv.orders[]` вместо `inv.tripRows` (унификация с SF/УПД).
3. **Жёсткий guard**: если `orders.length === 0` И статус документа `issued` (выпущен) → **запретить открытие шаблона печати**, показать пользователю «Документ выпущен без позиций — недопустимо. Свяжитесь с бухгалтером для пересчёта». Открывать пустой акт = создавать юр-ничтожный документ.

### 1.3 🔴 Захардкоженный «НДС 20%» — критично для УСН

**Код** (строки 129, 134):
```ts
<div className="total-row"><span>НДС 20%:</span><span>{money(inv.vatAmount)} ₽</span></div>
<div>Всего оказано услуг на сумму {money(inv.total)} руб. (НДС 20% включён).</div>
```

Ставка «20%» **захардкожена** в тексте, хотя в БД (`invoice_orders`, `vatRate`) хранится фактическая ставка.

**Юр-импликация:**
- ИП Бардин — на **УСН** (зафиксировано в [terms-of-service.md](terms-of-service.md) §13). На УСН **НДС не выставляется** (за исключением УСН с НДС 5%/7% по 244-ФЗ при доходе >60M ₽).
- Документ от ИП на УСН с указанием «НДС 20%» — **прямое нарушение** п. 5 ст. 173 НК (обязанность уплатить выставленный НДС в полном объёме без права на вычеты) и риск **переквалификации** деятельности с УСН на ОСНО с доначислением налогов.
- Заказчик (другое ИП на УСН) при этом **не имеет права** принять НДС к вычету.

**ТЗ для TransPult:**
1. Удалить хардкод. Брать ставку из `inv.vatRate`.
2. Если `inv.vatRate IS NULL` или `inv.includesVat=false` или `tax_regime` исполнителя не позволяет выставлять НДС → **не выводить** строку с НДС вообще, заменить на «**Без НДС**» (это требование п. 5 ст. 168 НК — при освобождении/неприменении НДС в счёте указывается «Без НДС»).
3. Применить связку с `invoice-spec.md §4` (правила НДС от tax_regime), реализованную в M-batch (`canIssueInvoiceType()`, `defaultIncludesVat()`, `allowedVatRates()`):
   - `tax_regime IN ('osno', 'usn_with_vat')` → НДС в документе.
   - `tax_regime IN ('usn_income', 'usn_income_expense', 'ausn', 'patent', 'npd')` → строка «Без НДС».
   - `unspecified` → блокировка выпуска документа (это уже реализовано в `issueDraftInvoice()`).
4. **На выпуске** документа уже происходит проверка `canIssueInvoiceType()` — но **шаблон печати** работает с уже выпущенным документом. Нужно либо доверять, что выпуск корректен, либо дополнительно валидировать на отображении (defense in depth).

### 1.4 🟡 Противоречие в формулировке НДС

Таблица: «Итого без НДС: X + НДС 20%: Y = ИТОГО: Z» — НДС **сверху**.
Подпись (строка 134): «(НДС 20% **включён**)» — НДС **в составе**.

Это противоречит само себе. По ст. 168 ч. 4 НК:
- Если НДС сверху → формулировка «Стоимость без НДС: X, в т.ч. НДС 20%: Y, всего к оплате с НДС: Z».
- Если НДС в составе → «Всего к оплате: Z (в т.ч. НДС 20%: Y, стоимость без НДС: X)».

**ТЗ для TransPult:**
- Использовать поле `invoice.includesVat`:
  - `true` (НДС в составе) → формулировка «Всего к оплате: {total}, **в т.ч. НДС {rate}%**: {vatAmount}».
  - `false` (НДС сверху) → формулировка «Стоимость без НДС: {subtotal}, НДС {rate}%: {vatAmount}, всего к оплате: {total}».

### 1.5 🟡 → 🟢 (на pilot) Подписи без должности

Строки 147-150, 153-156: только «ИСПОЛНИТЕЛЬ: ИП Бардин Георгий Дмитриевич» / «ЗАКАЗЧИК: ИП Никитин А.С.» без указания должности и места для расшифровки подписи.

**Юр-позиция (уточнённая после обмена с TransPult 10.06.2026):**

**До триггера** — не блокирует пилот, TransPult **ничего не делает**. У ИП Бардина шаблон отображается юридически корректно.

## §3 `print/ttn/[id]` — Товарно-транспортная накладная

### 3.1 🟡 Устаревшая форма № 1-Т

**Код** (строка 70): `<div style={{ fontSize: '7pt', color: '#555' }}>Форма № 1-Т</div>`

Форма 1-Т утверждена Постановлением Госкомстата от 28.11.1997 № 78. С **25 июля 2011** года применяется **транспортная накладная** по Постановлению Правительства РФ от 15.04.2011 № 272. С **01.09.2026** — обязательная ЭТрН в ГИС ЭПД.

**Юр-статус:** форма 1-Т не отменена, но **не является обязательной** для подтверждения перевозок (Письмо Минфина от 22.12.2011 № 03-03-10/123). При использовании 1-Т обязательно дополнительно оформляется **транспортная накладная** по форме 272 — иначе перевозка не считается надлежаще оформленной.

**ТЗ для TransPult:**
- Заменить «Форма № 1-Т» на «Транспортная накладная» по форме приложения к Постановлению Правительства РФ от 15.04.2011 № 272.
- Либо чётко указать, что это **дополнительный** документ (не основной).
- После 01.09.2026 — оба бумажных варианта применяются только при бумажном исключении из перечня Минтранса. Основная форма — ЭТрН (см. `print/etrn/`).

### 3.2 🟡 «КПП НЕ УСТАНОВЛЕНО» для ИП

**Код** (строка 17, 66):
```ts
kpp: process.env.NEXT_PUBLIC_CARRIER_KPP ?? 'НЕ УСТАНОВЛЕНО',
// ...
<div>ИНН {CARRIER.inn} / КПП {CARRIER.kpp}</div>
```

Если ИП и env `NEXT_PUBLIC_CARRIER_KPP` не задан (как и должно быть для ИП) → fallback `'НЕ УСТАНОВЛЕНО'`. Документ покажет: «ИНН 746003023587 / КПП НЕ УСТАНОВЛЕНО».

Это **нелепо** — у ИП КПП **не должно быть**. Контрагент при чтении документа подумает, что это ошибка.

**ТЗ для TransPult:**

- Применимо ко всем 5 шаблонам с тем же fallback.

### 3.3 🟡 → 🟢 (на own-fleet pilot) «Грузоотправитель (Перевозчик)» в одном поле

**Код** (строка 82): `<div>Грузоотправитель (Перевозчик):</div>` — две **разные** юридические роли в одной строке.

**Юр-позиция (уточнённая после обмена с TransPult 10.06.2026):**

- На **own-fleet пилоте** (ИП Бардин сам везёт собственный груз / для собственного клиента в режиме own) — формулировка **юридически приемлема**. Это особый случай, когда роли грузоотправителя и перевозчика совпадают (ст. 785 ГК + 259-ФЗ это допускают). Текущая модель данных корректно отражает реальность.
- При несовпадении ролей (см. ниже) — формулировка становится юридически некорректной.

**Переклассификация:** **P1 → P2 (условно, по трём триггерам)**.

**Триггеры (любой из):**
1. Появление **юрлица-клиента**, для которого ИП Бардин везёт **чужой груз** (грузоотправитель ≠ перевозчик).
2. Появление **субподряда** (см. Gap 2 в [subcontract-legal-analysis.md](subcontract-legal-analysis.md), сценарий 2 — «двойная ЭТрН»).
3. Появление **экспедиционного договора** (мы экспедитор, перевозчик — третье лицо; сценарий 3 в subcontract-analysis).

**До триггера** — не блокирует пилот, TransPult **ничего не делает**.

**На момент триггера** Jurist выпускает ТЗ на data-model:
- `order.shipper` (грузоотправитель: id + наименование/реквизиты)

## §7 `print/cancellation-act` и `print/claim-act` — приемлемые

Прочитал — структурно чистые:

**Минор-замечание** для `cancellation-act` (строка 63):
```ts
const reason = search.get('reason') || 'Груз не готов после подачи транспортного средства';
```

Дефолтная причина срыва подачи захардкожена. Если оператор забыл передать `?reason=...` в URL → выведется дефолтная причина, которая может **не соответствовать реальности**. Юр-риск минор: акт = двусторонний документ, подписант имеет возможность не подписать при неверной причине, но **до подписания** документ уже сформирован с потенциально ложной причиной.

**ТЗ для TransPult:**
- Заменить дефолт на `'(причина не указана)'` и **блокировать выпуск** документа, если причина пустая.

## §8 Корневые проблемы (повторяющиеся классы)

### 8.1 Захардкоженные ставки/значения вместо данных из БД

- НДС «20%» захардкожен в `act`, `invoice`.
- Банковские реквизиты захардкожены в fallback `invoice`.
- Форма «1-Т» захардкожена в `ttn`.
- «Грузоотправитель (Перевозчик)» захардкожен как одна строка в `ttn`.

**Корневая проблема:** шаблоны рендерят бизнес-значения как литералы, а не подтягивают из API.

### 8.2 Несогласованные fallback'и между шаблонами

- `invoice` → реальные реквизиты ИП Бардина.
- 5 других → `'НЕ УСТАНОВЛЕНО'`.

В одном комплекте документов — разные реквизиты при пустом env. Это **прямая опасность** в новых инсталляциях.

### 8.3 Отсутствие связки template ↔ invoice.type

Шаблон `act` открывается для документа любого типа (включая `upd`, `sf` и т.д.) → терминологическая каша и юридическая некорректность.

### 8.4 Бэкенд не агрегирует позиции для типов act/upd

Поле `tripRows`/`orders` либо не возвращается для типа `act`/`upd`, либо возвращается пустым → ничтожный документ.

### 8.5 Сырые enum'ы в печатной форме

Особенно критично для `etrn`, `signature-refusal` — это юр-значимые документы.
