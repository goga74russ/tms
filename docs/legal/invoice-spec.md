## 0. Scope

**Покрывает:**
- Юр-требования к модели данных счетов / счетов-фактур / актов в TMS
- Правила НДС от налогового режима организации
- FSM статусов и обязательные проверки переходов
- Связку invoice ↔ order (junction) и audit trail
- Корректировочные и исправленные документы
- Сроки выпуска и санкции за нарушение

**Не покрывает:**
- Внутреннюю архитектуру кода (выбор drizzle/transactions/etc) — это к TransPult
- UI / UX дизайн форм — к Design
- Приоритизация работ и сроки — к PM
- Конкретный текст оферты — отдельный документ (Terms of Service update)

**Нормативная база:**
- НК РФ ч. 2, гл. 21 (НДС): ст. 168, 169, 170
- Постановление Правительства РФ от 26.12.2011 № 1137 (форма СФ)
- Приказ ФНС России от 19.12.2018 № ММВ-7-15/820@ (электронный СФ)
- Приказ ФНС России от 21.12.2020 № ЕД-7-26/901@ (УПД)
- ФЗ-244 от 12.07.2024 (НДС для УСН-плательщиков с 2025)
- ФЗ-152 (ПДн в платёжных документах)

## 1. Enum `invoice_type` (7 значений)

```
payment           -- Счёт на оплату (расчётный документ-приглашение, не СФ)
advance           -- Счёт на предоплату (авансовый счёт)
sf                -- Счёт-фактура (ст. 169 НК)
upd               -- УПД (Универсальный Передаточный Документ, СФ+акт)
corrective_sf     -- Корректировочный СФ (ст. 169 ч. 5.2 НК) или исправленный СФ
corrective_upd    -- Корректировочный/исправленный УПД
act               -- Акт оказанных услуг (отдельно от СФ, для УСН без НДС)
```

**Юр-обоснование каждого типа:**

| Тип | Юр-природа | Кто выставляет | Когда |
|---|---|---|---|
| `payment` | Расчётный документ. **Не обязателен** по закону, бухгалтерская практика. | Любой | До или после оказания услуги |
| `advance` | Подтверждение требования авансового платежа. Влияет на признание дохода у УСН. | Любой | До оказания услуги |
| `sf` | Обязательна для всех плательщиков НДС в 5-дневный срок после реализации (ст. 168 НК ч. 3). Без неё покупатель не получит вычет НДС. | Только плательщики НДС | После реализации |
| `upd` | Заменяет связку СФ+акт. Юридически эквивалентна обоим. | Только плательщики НДС | После реализации |
| `corrective_sf` | Юридически отдельный документ. Регулирует исправления цены/количества **уже выпущенного** СФ. | Тот же что выпускал исходный | После выпуска исходного СФ |
| `corrective_upd` | То же для УПД | То же | То же |
| `act` | Акт без НДС-составляющей. Для УСН-плательщиков, ИП на ПСН, НПД. | Все, кто не выставляет СФ | После реализации |

**Дополнительное поле `correction_kind` (только при corrective_sf / corrective_upd):**

```
adjustment    -- Корректировочный СФ (КСФ): изменение цены или объёма после выпуска исходного.
              -- Исходный СФ ОСТАЁТСЯ валидным. Регулирует ст. 169 ч. 5.2 НК.
              -- Выпускается НА РАЗНИЦУ.
replacement   -- Исправленный СФ (ИСФ): ошибка в реквизитах исходного.
              -- Исходный СФ АННУЛИРУЕТСЯ в журнале. Регулирует п. 7 ПП РФ 1137.
              -- Выпускается на ПОЛНУЮ сумму взамен ошибочного.
```

Разница критическая для бухучёта: КСФ идёт в книгу покупок/продаж дополнительной строкой, ИСФ заменяет ошибочную строку с пометкой об аннуляции. **Это разные операции в 1С/СБИС**.

## 2. FSM `invoice_status`

```
draft → issued → paid_partial → paid_full
         ↓                  ↓
        cancelled         cancelled
         ↓
       corrected   (помечается, когда выпущен corrective_*)
```

**Матрица переходов (кто и при каких условиях):**

| Переход | Роли | Обязательные проверки |
|---|---|---|
| `*` → `draft` (создание) | logist / accountant / manager / admin | — |
| `draft` → `issued` | accountant / manager / admin | См. §3 «issued: обязательные поля». Для `sf`/`upd` — все плательщик/получатель/НДС/связка с order непусто. |
| `issued` → `paid_partial` | accountant / manager / admin | Поступила частичная оплата. `paid_amount > 0 AND paid_amount < total_amount`. |
| `issued` → `paid_full` | accountant / manager / admin | `paid_amount >= total_amount`. |
| `paid_partial` → `paid_full` | accountant / manager / admin | То же |
| `issued` → `cancelled` | manager / admin | Запрещён для `sf` / `upd` если payments_received > 0 — только через `corrective_*`. |
| `paid_*` → `cancelled` | admin only | Запрещён в принципе для `sf` / `upd` после оплаты. Возврат денег оформляется отдельным документом (возвратный СФ / акт возврата), а не cancellation. |
| `issued` → `corrected` | accountant / manager / admin | Автоматически при выпуске связанного `corrective_*` документа. |

**Запрещённые переходы (DB-level constraint):**

- `cancelled` → `*` — никогда. Аннулированный документ воскрешению не подлежит.
- `paid_full` → `paid_partial` — запрещено (откат оплаты только через возвратные документы).
- Любое UPDATE `total_amount`/`vat_amount`/`payer_id`/`payee_id`/`invoice_orders` после `status != 'draft'` — **запрещено**. Изменения возможны только через выпуск `corrective_*` или `cancelled` + новый документ.

Это **жёсткое правило** — закреплено в БД через trigger или check, не на уровне сервиса. Сервис-логика обходима, БД — нет.

## 3. Обязательные поля по статусам

### `draft`
- `invoice_type` (enum) — обязательно
- `payee_id` — обязательно (это мы или клиент, в зависимости от направления)
- `payer_id` — обязательно

**Достаточно для сохранения. Всё остальное — по мере заполнения.**

### `issued` (для всех типов)
- Все поля `draft` +
- `number` — внутренний номер документа. **Нумерация раздельная по `invoice_type`** (СФ свой ряд, payment свой — это требование п. 5.1 ст. 169 НК для СФ).
- `issued_at` — дата выпуска
- `total_amount` — общая сумма
- `currency` — валюта (default RUB)
- `includes_vat` — `true`/`false`
- `basis_text` — **текст основания**, обязательное поле для печати:
  - формат: «За транспортные услуги по заявке № X от ДД.ММ.ГГГГ»
  - либо: «За услуги по договору № X от ДД.ММ.ГГГГ, перевозки по реестру»
  - Без основания ФНС при проверке у клиента откажет в признании расхода (ст. 252 НК).
- `invoice_orders[]` — junction-записи, **не пусто**, Σ `allocated_amount = total_amount` (CHECK constraint)

### `issued` (дополнительно для `sf` / `upd`)
- `vat_rate` — ставка (0 / 5 / 7 / 10 / **22**; 20 — только для исторических документов с датой отгрузки ≤ 31.12.2025, см. §4 и §4.1). NULL запрещён для СФ.
- `vat_amount` — рассчитанная сумма НДС
- `payer_inn`, `payer_kpp` (если юрлицо), `payer_name`, `payer_address` — реквизиты покупателя
- `payee_inn`, `payee_kpp`, `payee_name`, `payee_address` — наши реквизиты
- `seller_signature_id` — ссылка на КЭП, которой подписан документ (если бумажный — null + флаг paper_form=true)

### `issued` (дополнительно для `corrective_sf` / `corrective_upd`)
- `related_invoice_id` — ссылка на исходный СФ. NOT NULL.
- `correction_kind` — `adjustment` | `replacement`. NOT NULL.
- Если `correction_kind = 'replacement'` (ИСФ) — исходный документ автоматически переводится в статус `cancelled` с пометкой `cancellation_reason='replaced_by:<this_id>'`.
- Если `correction_kind = 'adjustment'` (КСФ) — исходный остаётся `issued`, но получает флаг `has_corrections=true`.
- `correction_reason` — текст обоснования (свободный, но обязательный).

### `paid_partial` / `paid_full`
- `paid_amount` — сумма поступлений
- `payment_records[]` — ссылки на платёжные документы (платёжные поручения)

### `cancelled`
- `cancellation_reason` — обязательный текст

## 4. Правила НДС от налогового режима организации

> **🔴 ВНИМАНИЕ — основная ставка НДС изменена с 01.01.2026 (ФЗ от 28.11.2025 № 425-ФЗ): 20% → 22%.** Расчётная ставка 20/120 → 22/122. Таблица ниже — **актуальная (с 01.01.2026)**. Для документов с датой отгрузки до 31.12.2025 применяется старая ставка 20% — см. §4.1 «Историчность».

| `tax_regime` | Может выставлять `sf`/`upd`? | Default `includes_vat` в `customer_price` | Допустимые ставки НДС (с 01.01.2026) |
|---|---|---|---|
| `osno` | **Да, обязательно** | `true` | 0% / 10% / **22%** |
| `usn_income` | Нет | `false` | — |
| `usn_income_expense` | Нет | `false` | — |
| `usn_with_vat` (244-ФЗ) | **Да, обязательно** | `true` | 5% / 7% / **22%** (выбор плательщика, фиксируется в учётной политике) |
| `ausn` | Нет | `false` | — |
| `patent` | Нет | `false` | — |
| `npd` | Нет | `false` | — |
| `unspecified` | **Заблокировано** | без default'а, обязательный явный выбор | — |

> **Примечание по УСН:** ставки 5% (доход до 250 млн ₽) и 7% (250–450 млн ₽) — **без изменений** (повышение основной ставки на них не повлияло). Изменилась только основная ставка 20→22%, которую `usn_with_vat`-плательщик выбирает вместо 5/7. Порог освобождения УСН от НДС снижен до **20 млн ₽** за предыдущий год.

**Правила enforcement:**

1. При попытке создать `invoice_type IN ('sf','upd','corrective_sf','corrective_upd')` от организации с `tax_regime NOT IN ('osno','usn_with_vat')` — **отказ HTTP 422** с понятной ошибкой.
2. При попытке создать любой `invoice_type` от организации с `tax_regime='unspecified'` — отказ 422.
3. Default `includes_vat` берётся из tax_regime, но **редактируем пользователем** (есть legitимные сценарии экспорта/освобождения).
4. При несогласованности `tax_regime` и `vat_rate` (например, УСН-доходы и vat_rate=22%) — отказ 422.

**Особая логика для `usn_with_vat`:**
- При первом включении этого режима — UI должен запросить выбор ставки (5%/7%/22%), это фиксируется в `organization.usn_vat_rate`. Изменить можно только с нового налогового периода (1 января).
- При выставлении СФ ставка берётся из `organization.usn_vat_rate`, не выбирается каждый раз.

## 4.1. Историчность ставки НДС по дате отгрузки

**Юр-основание:** ст. 167 НК РФ — момент определения налоговой базы (и применимой ставки) — **дата отгрузки (реализации)** товаров/работ/услуг, не дата договора и не дата выставления документа.

### Правило определения ставки

| Дата отгрузки (реализации) | Основная ставка | Расчётная ставка («в т.ч. НДС») |
|---|---|---|
| **до 31.12.2025 включительно** | 20% | 20/120 |
| **с 01.01.2026** | 22% | 22/122 |

Льготная ставка 10% (продукты, детские товары, лекарства и т.д.) — **не изменилась** в обоих периодах.

### Что является «датой отгрузки» в модели TMS

Для транспортных услуг «дата отгрузки» = **дата фактического оказания услуги** = **дата завершения перевозки**:
- момент подписания **Титула 6 ЭТрН** (закрытие рейса перевозчиком), либо
- `trip.completedAt` (факт выгрузки / закрытие рейса).

**НЕ** использовать для выбора ставки:
- `invoice.createdAt` (дата создания документа) — может быть позже отгрузки;
- дату договора;
- дату аванса.

### ТЗ для TransPult

1. Функция выбора ставки: `resolveVatRate(taxRegime, shipmentDate, organizationUsnVatRate)`:
   - режимы без НДС (`usn_income`/`usn_income_expense`/`ausn`/`patent`/`npd`) → `null` (НДС не выставляется);
   - `usn_with_vat`:
     - **если `organizationUsnVatRate ∈ {5, 7}` → вернуть эту ставку** (не зависит от даты — выбор плательщика, зафиксированный в учётной политике на год; **приоритет над датой**);
     - иначе (выбрана основная ставка) → по дате: `shipmentDate ≤ 2025-12-31` → 20, `≥ 2026-01-01` → 22;
   - `osno` → по типу услуги: транспорт обычно 22 (≥2026) / 20 (≤2025); 10 если льготная категория; 0 если экспорт.
2. `allowedVatRates` в `packages/shared/src/invoice-fsm.ts` — расширить до набора, **включающего обе ставки** (для возможности выпуска корректировок/исторических документов): `osno → [0, 10, 20, 22]`, `usn_with_vat → [5, 7, 20, 22]`. Валидация при выпуске: ставка должна соответствовать дате отгрузки (20% только если отгрузка ≤ 2025, иначе 422).
3. `vatRate` default в `schemas.ts:105` — убрать жёсткий `.default(20)`; ставка обязательна и вычисляется по дате отгрузки, не дефолтится.
4. Server-PDF (`act-pdf`, `invoice-pdf`, `upd-pdf`) — убрать `?? 20`, передавать вычисленную ставку.

### Правило для счёта на несколько рейсов (Q1 — запрет смешивания периодов)

**Решение: запрет смешивания ставок в одном СФ/УПД (вариант B).**

Юр-основание: СФ отражает операции одного налогового периода; смешивание отгрузок 2025 (20%) и 2026 (22%) в одном документе — риск при камеральной проверке + усложнение книги продаж. Вариант «по позднейшей дате» — налогово неверен (декабрьский рейс не может облагаться ставкой 2026 года).

**Реализация:**
- При формировании `sf`/`upd`/`corrective_sf`/`corrective_upd` из `invoice_orders` (несколько рейсов) — проверить, что **все** даты отгрузки рейсов попадают в один ставочный период (либо все ≤ 31.12.2025, либо все ≥ 01.01.2026).
- При смешивании → **422**: «Счёт-фактура не может включать рейсы с разными ставками НДС (отгрузки 2025 и 2026 года). Разделите на отдельные документы».
- Для `act` (акт) и `payment` (счёт на оплату) — ограничение **не применяется** (нет НДС-разбивки по строкам, либо без НДС у УСН).
- **Построчные ставки в одном СФ (вариант C)** — намеренно НЕ реализуем в MVP (overkill для разовых транспортных услуг). Если появятся длящиеся декабрь-январь сделки — отдельная задача.

### Edge-кейс: аванс 2025 / отгрузка 2026

**Сценарий (редкий для услуг, но логику заложить):** аванс получен в 2025 году (НДС с аванса 20%, расчётная 20/120), фактическая перевозка завершена в 2026 году (отгрузка → ставка 22%).

**Правильное поведение (по разъяснениям Минфина о переходных договорах):**
- НДС с аванса в 2025 — по ставке 20/120 (на момент получения аванса).
- При отгрузке в 2026 — итоговый НДС по ставке 22%.
- Разница (22% − 20% от стоимости) — **доначисляется**, оформляется корректировочным документом, либо допсоглашением о цене (кто несёт разницу — продавец или покупатель — определяется договором).

**Для MVP:** этот кейс **не блокирует пилот** (мы оказываем услуги по факту, предоплата редка). Но `resolveVatRate` должна корректно работать от даты отгрузки, чтобы кейс не сломал расчёт. Детальную обработку аванс-разницы — отдельной задачей, если появится предоплатный сценарий.

### Юр-импликация (почему это P0)

С 22.01.2026 (первая отгрузка 2026 года + 5-дневный срок СФ) любой СФ/УПД, выпущенный с НДС 20% за отгрузку 2026 года, содержит **неверную сумму налога**:
- продавец (мы/клиент-перевозчик) недоплачивает НДС в бюджет → ст. 122 НК (штраф 20-40% от неуплаты) + пени;
- покупатель принимает к вычету неверную сумму → риск отказа в вычете при проверке.

**Если система уже выпускала реальные документы с 01.01.2026 по ставке 20%** — нужна инвентаризация выпущенных документов и **корректировка через КСФ** (`correction_kind='adjustment'`) на разницу ставки. Это отдельная ретроспективная задача — проверить с бухгалтером клиента.

## 5. Корректировочные vs исправленные документы

### Корректировочный СФ (КСФ) — `correction_kind='adjustment'`

**Когда:** изменилась цена и/или количество **после** выпуска исходного СФ. Например:
- Клиент вернул часть груза → перевозчик уменьшает счёт
- Клиент согласовал доплату → перевозчик увеличивает счёт
- Обнаружена недоплата по тарифу

**Что делается:**
- Исходный СФ **остаётся валидным** (`status='issued'`, флаг `has_corrections=true`)
- Выпускается **новый документ** типа `corrective_sf` с `related_invoice_id`
- Сумма КСФ = **разница** (положительная или отрицательная) между исходным и новым итогом
- В книге продаж у нас и книге покупок у клиента появляется **дополнительная строка**

**Pre-conditions:**
- Исходный СФ должен быть в статусе `issued` или `paid_*`
- Должен быть документ-основание корректировки (доп.соглашение, акт сверки, претензия) — поле `correction_basis_artifact_id`

### Исправленный СФ (ИСФ) — `correction_kind='replacement'`

**Когда:** обнаружена **ошибка в реквизитах** исходного СФ:
- Неверный ИНН / КПП / название организации
- Неверная дата / номер договора в `basis_text`
- Опечатка в наименовании услуги

**Что делается:**
- Исходный СФ **аннулируется** (`status='cancelled'`, `cancellation_reason='replaced_by:<new_id>'`)
- Выпускается **новый документ** типа `corrective_sf` (correction_kind=replacement) с теми же реквизитами **в исправленной форме**
- Сумма ИСФ = **полная сумма** (не разница), точно такая же как у исходного СФ (только реквизиты другие)
- В книге продаж у нас — аннуляция исходной строки + новая строка

**Pre-conditions:**
- Аналогично КСФ + дополнительно `correction_reason` должен указывать **какой именно реквизит исправлен**

### Важно

**Запрет на UPDATE исходного документа** — это юр-критическое требование. ФНС при проверке может запросить **все версии** документа за период. Если у нас была правка `UPDATE invoices SET total = 200 WHERE id = X` — мы это **не сможем доказать** регулятору, и сделка может быть переквалифицирована.

**TransPult'у:** механизм enforcement — БД-trigger на UPDATE с whitelist разрешённых полей (status переходы, payment_records, флаги).

## 6. Сроки выпуска

| Тип | Срок | Норматив | Санкция за нарушение |
|---|---|---|---|
| `sf` (СФ) | **5 календарных дней** от даты реализации | ст. 168 ч. 3 НК | Покупатель может не получить вычет НДС, но штрафа для продавца за просрочку выпуска как такового нет. Однако ФНС при проверке трактует регулярные просрочки как «нарушение учётной политики» с риском доначисления. |
| `upd` | То же | То же | То же |
| `corrective_sf` | **5 дней** от даты согласия покупателя с изменением (дата подписания доп.соглашения или акта сверки) | п. 10 ст. 172 НК | То же |
| `payment` | Срок не регламентирован | — | — |
| `advance` | Срок не регламентирован, но СФ на аванс — **5 дней** от поступления аванса | ст. 168 ч. 3 НК | Тот же риск |
| `act` | Срок не регламентирован, но «в разумный срок» (обычно 5-10 дней от завершения работ) | ст. 720 ГК | Спор о признании оказания услуг |

**Логика TransPult'у:**
- При попытке выпуска СФ позже 5 дней от `order.completed_at` (или `trip.completed_at` для УПД) — **warning** в UI, не block. Дать кнопку «Подтвердить выпуск с просрочкой» с обязательным указанием причины.
- В аудит-trail зафиксировать факт просрочки и причину.
- В административном дашборде должен быть отчёт «СФ выпущенные с просрочкой» — для контроля бухгалтером.

## 7. PDF-шаблоны

**Что Jurist даёт:** чек-лист обязательных реквизитов со ссылкой на нормативку.

**Что Jurist НЕ делает:** не верстает PDF, не пишет XSLT/HTML-шаблоны. Это работа Design и TransPult.

### СФ — обязательные реквизиты (Постановление 1137 от 26.12.2011, актуальная редакция)

Чек-лист (ВСЕ должны быть):
1. Порядковый номер и дата составления
2. Наименование, адрес, ИНН, КПП продавца
3. Наименование, адрес, ИНН, КПП покупателя
4. Наименование, адрес грузоотправителя
5. Наименование, адрес грузополучателя
6. Номер платёжно-расчётного документа (при авансе)
7. Идентификатор гос.контракта / договора (при наличии)
8. Наименование валюты
9. Код вида товара (для экспорта в ЕАЭС)
10. По каждой строке: наименование услуги, единица измерения, количество, цена за единицу, стоимость без НДС, налоговая ставка, сумма НДС, стоимость с НДС
11. Страна происхождения и номер таможенной декларации (для импорта)
12. Подписи руководителя и главного бухгалтера (или уполномоченных лиц по приказу) **либо** усиленная квалифицированная электронная подпись

### УПД — обязательные реквизиты (Приказ ФНС ММВ-7-15/820@)

Чек-лист идентичен СФ + дополнительно реквизиты акта:
1. Дата фактической отгрузки/оказания услуги
2. Подписи передающей и принимающей стороны
3. Должности подписантов

### КСФ — дополнительно (ст. 169 ч. 5.2 НК)

1. Слова «Корректировочный счёт-фактура» в наименовании
2. Порядковый номер и дата КСФ
3. Порядковый номер и дата исходного СФ (поле «к счёту-фактуре №… от…»)
4. Реквизиты как у исходного
5. По каждой строке: количество/цена/стоимость **до** изменения, **после** изменения, **разница** (увеличение или уменьшение)
6. Подпись

### ИСФ — дополнительно

1. Слова «Исправление №… от…» в наименовании
2. Номер и дата исходного (исправляемого) СФ
3. Все реквизиты как у нового СФ (полная замена)

## 8. Аудит-трейл и неизменяемость

### Что обязательно сохранять

| Объект | Срок хранения | Норматив |
|---|---|---|
| Все версии invoice (исходные + корректировки + исправления) | **5 лет** от даты последнего изменения | ст. 23 ч. 1 п. 8 НК (4 года для налогов) + ст. 29 ч. 1 ФЗ-402 «О бухучёте» (5 лет) |
| `invoice_history` — журнал изменений каждого поля | 5 лет | То же |
| `invoice_orders` junction — все изменения allocated_amount | 5 лет | То же |
| Платёжные документы (`payment_records`) | 5 лет | ФЗ-54 ст. 4.1 |
| КСФ / ИСФ + ссылка на основание корректировки | 5 лет | То же |
| Журнал доступа к invoice (кто читал/просматривал) | 5 лет рекомендуется, 1 год обязательно | ФЗ-152 (для ПДн) |

### Минимальная схема `invoice_history`

```sql
CREATE TABLE invoice_history (
    id uuid PRIMARY KEY,
    invoice_id uuid NOT NULL REFERENCES invoices(id),
    operation varchar(20) NOT NULL,           -- 'create' | 'update' | 'status_change' | 'cancel'
    field_name varchar(64),                   -- какое поле изменилось (если update)
    previous_value jsonb,                     -- старое значение
    new_value jsonb,                          -- новое значение
    changed_by_user_id uuid REFERENCES users(id),
    change_reason text,                       -- обязательно для любых изменений после issued
    changed_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_invoice_history_invoice ON invoice_history(invoice_id, changed_at DESC);
```

Заполняется **автоматически** через DB-trigger или ORM hook на любой UPDATE/INSERT/DELETE invoices/invoice_orders. **Не через сервис-слой** — он обходим.

### Что НЕ ДОЛЖНО меняться

После `status='issued'`:
- `number`, `issued_at`, `total_amount`, `vat_amount`, `vat_rate`, `payer_*`, `payee_*`, `currency`, `includes_vat`, `basis_text`, `invoice_orders[]`, `allocated_amount`

Допустимо менять (через FSM):
- `status` (по FSM)
- `paid_amount`, `payment_records` (при поступлении оплаты)
- `has_corrections`, `cancellation_reason` (через FSM)

## 11. Что выходит за рамки этого документа

Эта спецификация — **минимум** для корректной работы счетов в TMS. Не покрывает:

- **Налоговые регистры** (книга продаж, книга покупок, журнал учёта полученных и выставленных СФ) — это **отдельная фича** для бухгалтерского экспорта. Будет отдельный документ `tax-registers-spec.md` когда дойдём до неё.
- **Электронные счета-фактуры через оператора ЭДО** (Приказ ФНС ММВ-7-15/820@) — это пересечение invoice-логики с ЭДО-логикой. Будет отдельный документ когда подключим первого реального ЭДО-оператора.
- **Возвратные документы** (СФ на возврат, акты возврата) — отдельная FSM-ветка, в MVP делаем через `corrective_sf` с отрицательной суммой, в зрелой версии — отдельный тип.
- **Многовалютные операции** — в MVP только RUB. Курсовые разницы — отдельная задача.

Все эти расширения — **после первого пилота**. Не блокеры 01.09.2026.
