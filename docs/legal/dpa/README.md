# DPA (Data Processing Acceptances) — тексты согласий по провайдерам

**Версия раздела:** 1.0
**Дата создания:** 2026-05-23
**Владелец:** Jurist (юр-советник проекта)

---

## Что это

При подключении организацией каждой интеграции (Контур.Диадок, Wialon, Госключ и т.д.) администратор клиента видит **отдельный экран с описанием передаваемых данных** и принимает согласие явным нажатием. Это требование 152-ФЗ ст. 9 (письменное согласие на обработку ПДн в электронной форме).

Эти тексты — то, что показывается в UI на шаге 1 подключения провайдера.

## Frontmatter-метаданные

Каждый файл начинается с YAML-блока, машиночитаемого для UI:

```yaml
---
provider_id: diadoc                    # совпадает с ProviderName в enums.ts
provider_label: Контур.Диадок          # отображаемое имя
category: edi                          # категория интеграции
owner: client                          # client | vendor
version: 1.0                           # семантическая версия текста
effective_from: 2026-05-23             # дата вступления в силу
requires_acceptance: true              # показывать DPA-шаг
---
```

## Версионирование

**Семантическое:**
- **major** (1.0 → 2.0) — меняются категории ПДн или цели обработки. Все существующие согласия **переподписываются**.
- **minor** (1.0 → 1.1) — добавляются юр-уточнения, ссылки, контакты. Существующие согласия **остаются валидными**, новые подписывают новую версию.
- **patch** (1.0 → 1.0.1) — опечатки, формулировки без юр-эффекта. Не требует переподписания.

**При любом изменении** — обновляется `effective_from` и `version` в frontmatter.

## Связь с БД

Поле `dpa_acceptances.dpaVersion` хранит `version` из frontmatter на момент принятия. Поле `dpa_acceptances.dpaContentHash` — SHA-256 от полного содержимого markdown-файла на момент подписания (для proof-в-суде, что пользователь видел именно эту версию).

**TransPult:** при коммите изменения в файл DPA — CI должен прогонять сравнение хешей и пересчитывать `version` если major/minor-change. Если в файле обновился только `effective_from` без bump'а `version` — fail в CI.

## Структура текста каждого DPA

Стандартизированная (для единообразия UI и юр-defense):

1. **О провайдере** — legal name, ИНН/ОГРН, юр-адрес, ссылка на их Privacy Policy
2. **Какие данные передаются** — категории ПДн по 152-ФЗ
3. **Цели обработки** — юр-обоснование передачи
4. **Правовое основание** — конкретный пункт ст. 6 152-ФЗ
5. **Срок хранения у провайдера**
6. **Трансграничная передача** — да/нет, юрисдикция
7. **Право субъекта на отзыв** + последствия
8. **Контакты для запросов**
9. **Текст подтверждения** (для UI-чекбокса)

## Сценарии client vs vendor

- **owner: client** (Диадок, Контур.Подпись, Госключ, Wialon) — credentials заводит admin клиента-перевозчика, провайдер договорно работает с клиентом. **TMS** — обработчик, **клиент** — оператор ПДн водителей/получателей. Текст DPA — это согласие admin'а клиента на то, что TMS передаст ПДн в провайдер.

- **owner: vendor** (ЮKassa, Mail.ru SMTP) — credentials наши, договор с провайдером — у нас. Это используется для биллинга самого TMS (клиент платит нам). **TMS** — оператор, **провайдер** — обработчик. Текст DPA — это уведомление admin'а клиента, что **его реквизиты** и email пойдут в наши платёжные/email-инфраструктуру.

В UI эти два случая визуально различаются: для **client** — заголовок «Подключение к [провайдер]», для **vendor** — заголовок «Использование сервисов TMS».
