# ЭПД: дельта до XSD-сертификации

_Обновлено: 2026-06-23. Источник истины — прогон `apps/api/scripts/xsd-delta.ts`._

## Что уже сделано (этот заход)

1. **Завендорены реальные XSD-схемы ФНС** → `apps/api/src/assets/etrn-schemas/`
   (поставляются в Docker-образ через существующий `COPY src/assets → dist/assets`).
   Линейка приказа **ЕД-7-26/1065@** от 09.12.2021, ВерсФорм **5.01**:
   - `973_01..973_08` — ЭТрН (8 титулов);
   - `974_01..974_03` — электронная сопроводительная ведомость;
   - `975_01..975_04` — электронный заказ-наряд.
2. **Подключён настоящий XSD-валидатор** (`apps/api/src/lib/xsd-schema-validator.ts`)
   на базе `xmllint-wasm` (WASM-порт libxml2, без native-зависимостей).
   Декодирует схемы windows-1251 → UTF-8, валидирует против реальной XSD,
   возвращает ошибки libxml2 как есть.
   - До этого `xsd-validator.ts` делал лишь структурную проверку
     (`fast-xml-parser`) — ловил grossly malformed XML, но НЕ сверял с XSD.
3. **Измерена дельта** — `generateETrN` пока НЕ проходит XSD (см. ниже).

## Измеренная дельта — ЭТрН Титул 1

Прогон `generateETrN` (Титул 1) против `ON_TRNACLGROT_1_973_01_05_01_02.xsd`,
**7 ошибок** на уровне `<Документ>` (валидатор останавливается на первом
несоответствии структуры, поэтому глубже дерево пока не проверено):

| Что не так | Наш генератор | Требование XSD ФНС |
|---|---|---|
| Атрибуты `<Документ>` | `ДатаДок`, `НомДок` | **не разрешены** на этом элементе |
| Обязательные атрибуты `<Документ>` | отсутствуют | **`КНД`, `ПоФактХЖ`, `ДатИнфГО`, `ВрИнфГО`** |
| Тело документа | `<СведТранспортнойНакладной>` | **`<СодИнфГО>`** (+ опц. `<ОснДовОргСост>`) |

Реальные имена участников в схеме: `СвГО` (грузоотправитель), `СвГП`
(грузополучатель), `СвПер` (перевозчик), `СвЗак` (заказчик), `МршПрвз`
(маршрут), `ПутевойЛист`, `Подписант`. Наши `СвУчаст/Отправитель/Получатель`
— упрощения, в XSD их нет.

**Вывод:** текущие генераторы — структурно осмысленный макет, но любой
ЭДО-оператор отклонит их на приёме. Это не догадка — измерено libxml2 против
официальной XSD.

## Дорожная карта до сертифицируемого XML

1. **Переписать `generateETrN` Титул 1** под `СодИнфГО`-дерево, итерируя через
   `npx tsx scripts/xsd-delta.ts` до `valid: true`. Семантику обязательных
   веток брать из `pril1.md` (человекочитаемое описание формата 1065@).
2. Повторить для Титулов 2/5/6 (приём/выдача) — схемы уже на месте.
3. **ЭЗЗ (приказ 108@) и ЭПЛ (приказ 116@)** — XSD этих форматов в репо **нет**
   (1065@ покрывает только 973/974/975). Источник: nalog.gov.ru (страницы
   приказов) либо **комплект Контура вместе с ключами** (ожидается). После
   получения — завендорить рядом и провалидировать `generateEZZ`/`generateEPL`
   тем же циклом.
4. Подключить `validateEtrnAgainstXsd` в гейт перед отправкой в ЭДО
   (сейчас гейт — структурный; жёсткий XSD-блок включаем, когда генераторы
   станут зелёными, иначе сломаем выгрузку-предпросмотр).

## Почему не «наполовину» сейчас

Каждый титул — глубокое дерево с co-constraint'ами (Schematron внутри XSD).
Полупереписанный генератор хуже честного макета: он выглядит «почти готовым»,
но всё так же не проходит. Поэтому сначала — настоящий движок валидации
(сделано), затем — приведение генераторов титул-за-титулом до зелёного XSD
(удобно совместить с тестовым контуром Контура для end-to-end проверки).
